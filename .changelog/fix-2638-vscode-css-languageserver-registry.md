section: Fixed
---

- **Managed CSS/HTML Language Server installs no longer target dead or mismatched npm packages, and a genuine install failure is no longer silently folded into "toolchain absent" (closes #2638)** — `clients/installer/index.ts`'s `TOOLS` registry pointed `vscode-css-languageserver` at a bare npm package of the same name, unpublished from the registry on 2021-07-22 (`npm view vscode-css-languageserver` → `E404`); `ensureTool("vscode-css-languageserver")` could never succeed. Review of the fix (asserting every entry's `binaryName` is actually in its resolved package's published `bin` map) found the identical defect class on `vscode-html-languageserver-bin`: it still resolves on npm, but hasn't been republished since 2018 and its `bin` is named `html-languageserver`, not the `vscode-html-language-server` the entry's `checkCommand`/`binaryName` expect. Both now ship from `vscode-langservers-extracted` — the same unpinned package the sibling `vscode-json-language-server` entry already installs, which bundles the `vscode-css-language-server`/`vscode-html-language-server`/`vscode-json-language-server`/`vscode-eslint-language-server`/`vscode-markdown-language-server` bins together; `npm view vscode-langservers-extracted engines` reports no floor, so (unlike `typescript-language-server`, #2633) there is no EBADENGINE reason to pin either. The installer's stale, self-contradicting "manual install required" header comment (naming a dead package for CSS, and listing several tools as manual that are already auto-installed above it) is deleted rather than re-derived — `TOOLS` is the single source of truth. Separately, `installNpmTool`'s own catch swallowed the real npm error (E404, EBADENGINE, network failure) and only logged it, so `getInstallFailureReason`/`getInstallAttempt` fell back to a generic "install failed" for every kind of failure alike; it now records the actual message. `scripts/smoke-tools.mjs`'s `--lsp` lane used that same generic bucket to classify EVERY `ensureTool` failure as "unavailable" (⚠, not a failure) — indistinguishable from a genuinely-absent toolchain (no Rust for rust-analyzer) — so the nightly saw `ensureTool(vscode-css-languageserver) → UNAVAILABLE` every night without ever going red; an npm-strategy failure (this harness itself runs under Node, so Node can never be "absent") or a pip/gem failure with its toolchain confirmed present is now reported as a genuine ✗ fail, carrying the installer's real error text.

  New tests: `tests/clients/installer/registry-resolve.integration.test.ts` (network-gated, `PI_LENS_INTEGRATION=1`) asserts every `installStrategy: "npm"` TOOLS entry resolves its pinned-or-latest version on the real npm registry AND that the entry's `binaryName` is in that version's published `bin` map; `tests/clients/installer/managed-tool-ids.test.ts` gains network-free pin assertions for both corrected entries; `tests/clients/install-attempt-evidence.test.ts` gains a case for the real-error-recording fix; `tests/scripts/smoke-tools-genuine-install-failure.test.ts` unit-tests the new classification decision. All proven red-first against the pre-fix registry/installer/smoke-tools code (PR body has the transcripts, including a live `node scripts/smoke-tools.mjs --lsp css --install` run against the real npm registry going from a false-green ⚠ skip to a correctly-red ✗ fail, then to a genuine ✓ pass once the registry fix is restored).
